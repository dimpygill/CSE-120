Programming Language Design

A Comparative Study: MS SQL Server (T-SQL) vs. C, C#, and Python

When studying programming language design, we often analyze general-purpose languages (GPLs) like C, C#, and Python. However, looking at specialized environments like MS SQL Server (T-SQL) provides fascinating insights into how language syntax, semantics, and execution models shift when optimized for data management.

1. Domain-Specific Languages (DSLs) vs. General-Purpose Languages

A fundamental classification in language design is distinguishing between tools built to solve any computational problem versus those engineered for a single domain.

  • C, C# & Python (GPLs): Designed to build everything from operating systems to web apps using imperative, object-oriented, or functional paradigms.
  • SQL / T-SQL (DSL): A hybrid language. It combines a declarative query language with an embedded procedural scripting extension (T-SQL). Instead of telling the computer how to step through memory (imperative), you declare what data you want, letting the database engine build the optimal execution path.

2. Syntactic Order vs. Semantic Evaluation Order

Most languages follow the principle of least surprise: code written top-to-bottom executes top-to-bottom. SQL completely subverts this expectation.

SELECT Department, COUNT(*) 
FROM Employees 
WHERE Salary > 50000 
GROUP BY Department 
ORDER BY COUNT(*);

Syntactically, the query starts with SELECT. However, semantically, the database engine evaluates the clauses in a completely different order:

  1. FROM & JOIN (Gather the data tables)
  2. WHERE (Filter individual rows)
  3. GROUP BY (Aggregate rows)
  4. HAVING (Filter groups)
  5. SELECT (Compute expressions and column choices)
  6. ORDER BY (Sort final presentation)

Python Example: Statement Order and Operator Precedence

number = 5
print("First:", number)
result = 2 + 3 * 4
print("Result:", result)

Output: First: 5, followed by Result: 14 (on separate lines). Python executes these statements in sequence. Within the arithmetic expression, multiplication has higher precedence than addition, so 3 * 4 is grouped before adding 2. Operator precedence determines grouping; it should not be confused with the order in which operands with side effects are evaluated.

C# Example: Statement Order and Expression Evaluation

using System;

int number = 5;
Console.WriteLine($"First: {number}");
int result = 2 + 3 * 4;
Console.WriteLine($"Result: {result}");

Output: First: 5, followed by Result: 14 (on separate lines). Like Python, C# normally executes these statements in sequence. Multiplication binds more tightly than addition. C# also specifies left-to-right evaluation of operands; precedence controls how an expression is grouped, not an arbitrary reordering of its operand evaluations.

Compare with SQL

In Python and C#, the examples demonstrate sequential statements and arithmetic operator precedence. In SQL, the logical query processing order explains why FROM and WHERE logically precede SELECT, even though SELECT appears first in the written query. This is a conceptual order, not a guarantee that SQL Server physically executes each clause in that sequence: its optimizer can rearrange operations while preserving the query's required semantics.

Logical Processing vs. Physical Execution in SQL Server

Logical processing order is a conceptual model for understanding the result required by a query. Physical execution is the actual plan chosen by the SQL Server query optimizer. The optimizer may use indexes, choose different join orders, and combine operations while preserving the required query semantics.

Example 1: Filtering employees

Assume the Employees table contains these rows:

EmployeeIDNameDepartmentSalary
1AliceIT70000
2BobHR40000
3CharlieIT80000
4DavidHR60000
SELECT Name, Department
FROM Employees
WHERE Salary > 50000
ORDER BY Name;

Conceptual logical order: (1) FROM identifies Employees; (2) WHERE keeps rows with Salary above 50000; (3) SELECT chooses Name and Department; (4) ORDER BY sorts the result by Name.

Result:

NameDepartment
AliceIT
CharlieIT
DavidHR

One possible physical plan: If an appropriate index exists on Salary, SQL Server might use an Index Seek to find salaries above 50000, retrieve Name and Department if they are not covered by the index, and then sort by Name. Another plan might scan the table and filter rows. The optimizer chooses based on available indexes, statistics, and estimated costs. Both plans must return the same required result.

Example 2: Reordering joins

SELECT E.Name, D.DepartmentName
FROM Employees AS E
JOIN Departments AS D
    ON E.DepartmentID = D.DepartmentID
WHERE D.DepartmentName = 'IT';

Logical interpretation: Join employees with their departments, then retain only rows where the department name is IT.

Possible physical plan: SQL Server may first locate the IT row in Departments, then find matching employees by DepartmentID, even though Employees appears first in the query. This can avoid processing unnecessary rows. The exact plan is not guaranteed.

Three Different Kinds of Order

Syntactic order: The order in which SQL clauses are written (for example, SELECT before FROM).

Logical processing order: The conceptual rules defining the query result (for example, FROM and WHERE logically precede SELECT).

Physical execution order: The actual operators and access paths selected by the SQL Server optimizer to compute that result.

Try it in SSMS: Enable Include Actual Execution Plan, execute a query, and inspect the operators shown. The plan can vary with table size, indexes, statistics, and server configuration.
